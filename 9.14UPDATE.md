Task 1 本身没有代码去“关闭手机热点”或者让其他电脑主动断开 Wi-Fi。 你看到其他电脑从热点掉线，更可能是手机热点在 MongoDB 的持续局域网流量下不稳定；同时还有一个更重要的问题：你日志里的 secondary_failure / primary_failure / network_partition 其实都没有真正执行成功。



我根据你说的情况（热点环境下网络本身不太稳定，长时间、高频率的读写压测容易把热点搞崩，而不是"故障注入"本身的问题）对 `task1_read_your_writes.py` 做了以下调整：

**主要改动**

1. `N`：200 → 30（每个 Config 只跑 30 次写读对，大幅减少总请求量）
2. `PROGRESS_EVERY`：20 → 5（配合更少的迭代数，保证还能看到进度）
3. 后台写压发生器（`BackgroundLoadGenerator`）：
   - 每批文档数 50 → 10（新增常量 `BACKGROUND_LOAD_BATCH_SIZE`）
   - 每批之间新增 `BACKGROUND_LOAD_SLEEP_SECONDS = 0.3` 的间隔，避免持续跑满热点带宽
4. 适当调大了几个超时阈值（Config A 的 `find_one max_time_ms` 5000→8000ms，Config B 的 `find_one max_time_ms` 10000→15000ms，写入 `wtimeout` 10000→15000ms），减少"热点本身抖动"被误判为 `availability_loss` 的概率

这些改动不影响实验设计和结论逻辑（Config A 弱一致性、Config B 强一致性的对比依然成立），只是把每轮实验对网络的压力和总耗时降下来。

### 出现问题
运行本身没有崩溃、四个场景全部走完，也生成了报告需要的数据，从代码执行角度是**正常**的。但从实验结果角度看，有两个点值得你注意，写报告时要如实说明：

**1. "normal" 场景下 Config B 出现了 8/30 次可用性丢失，这不太正常**

正常场景没有注入任何故障，理论上 Config B（因果会话 + majority）应该稳定通过。但日志里 i=22~29 全是 `ServerSelectionTimeoutError`。结合前后台还在跑写负载（每 0.3s 写 10 条），这更像是手机热点网络本身的抖动/丢包，或者 pinned 的那台 secondary 被后台写负载压得一时追不上因果读点、在 15s 超时内没赶上——不是"设计上预期"的失败,而是环境噪声。写报告时不能把这 8 次简单归为"Config B 也有可用性代价"当正常结论,建议加一句说明:热点网络在高背景负载下会给强一致性配置引入额外的可用性抖动,这是环境限制而非该配置本身的固有特性,并考虑之后重跑一次 normal 场景确认是不是偶发。

**2. `secondary_failure` 和 `network_partition` 两个场景，Config A 和 Config B 都是 30/30 全部可用性丢失，0 个有效迭代**

这是设计上的必然结果,因为读操作被 pin 死在那个被 stop/disconnect 的具体节点上——它整个不可达,不管走哪个配置读都读不到,不算 bug。但这意味着**这两个场景实际上完全没有产生任何"是否违反 RYW"的证据**，只证明了"目标副本彻底下线时两种配置都会牺牲可用性"这一点（这本身也是一个合法、值得写进报告的 CAP 权衡结论，只是不能和"stale/pass"混为一谈）。写报告时这两行的解读应该是"验证了不可用而非验证了一致性"，而不是像 primary_failure/normal 那样去比较 violation rate。

如果你想让 `secondary_failure`/`network_partition` 场景也能观察到"部分退化但仍可读"的行为（比如读一个没被杀掉、但因为集群压力而落后的健康 secondary），需要改一下 pin 策略——但那是设计选择问题，不是当前代码的错误。目前这份输出可以直接用，只是解读时按上面两点措辞会更严谨。
